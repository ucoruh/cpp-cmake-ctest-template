# Daily workflow

## Branch, commit, push

```bash
git checkout -b feature/inventory-add-stock
# ... edit files ...
git status --short
git add src/inventory/ src/tests/inventory/
git commit -m "Add Inventory::addStock with negative-quantity validation"
git push -u origin feature/inventory-add-stock
```

Open a pull request into `main` on GitHub. `.github/workflows/cpp.yml` runs automatically (configure,
build Release, `ctest`) on the push and on the PR - it is intentionally lean (no Doxygen, no
coverage, no site) so it finishes in a couple of minutes and does not burn Actions minutes on every
push; see [releases.en.md](releases.en.md) for the minutes budget.

## Format your code before committing

```bat
5-format-code.bat
```

```bash
astyle --options=astyle-options.txt --recursive "*.h" "*.cpp"
```

If you installed the git hooks (`1-configure-git-hooks.bat`, once), `pre-commit` runs AStyle
automatically on staged `.c/.cpp/.h/.cs/.java` files and re-stages the formatted result.

## Where everything lands

| What | Where |
| --- | --- |
| Built binaries | `publish_win/`, `build_win/build/{Debug,Release}/` (Linux: `publish_linux/`, `build_linux/build/...`) |
| All reports + docs, source for the site | `docs/` (see [../reports.md](../reports.md)) |
| The built site (open this) | `site/index.html` |
| Packaged binaries + reports (`.tar.gz`) | `release_win/` / `release_linux/` |
| Coverage/documentation-coverage trend history used by ReportGenerator | `report_test_hist_win/`, `report_doc_lib_hist_win/`, etc. (not committed - see `.gitignore`) |

None of `docs/*` (except the hand-written `.md` pages), `site/`, `build_*`, `publish_*`, `release_*`
are committed - they are all regenerated by the build scripts (see `.gitignore`).

## Reading a report quickly

1. Open `site/index.html` (or `docs/reports.md` directly).
2. **Red/orange lines** in a coverage report = not executed by any test - either add a test or
   understand why (e.g. genuinely unreachable defensive code).
3. Compare the ReportGenerator number and the native tool's number for the same report (e.g.
   `coveragereportlibwin` vs `coveragenativelibwin`) - they should be close; a big difference usually
   means one of the two is looking at stale data (re-run the build).
4. `testresultswin/index.html` (or `testresultslinux/...`) - pass/fail per test case, no coverage
   information; this is the one to check first if the build script reported failing tests.

## CI (GitHub Actions)

`.github/workflows/cpp.yml` builds and tests on every push/PR (Windows + Ubuntu, Release only, no
report generation - see above). `.github/workflows/release.yml` is the slow, full pipeline
(Doxygen + reports + site + a GitHub Release); it only runs on a `v*` tag or a manual
`workflow_dispatch` - see [releases.en.md](releases.en.md) for why, and prefer the local
`10-release.bat`/`.sh` script day to day (no Actions minutes used).
